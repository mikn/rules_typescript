### Added

- **`ts_worker_types` generates a Cloudflare worker's
  `worker-configuration.d.ts` from its wrangler config, as a build output.**
  The bindings a worker reads off `env` are declared in the wrangler config,
  and `wrangler types` is what turns them into an `Env` interface plus the
  runtime's own globals for the config's compatibility date. A worker repo
  checks the file in, re-runs the command by hand and keeps a hook or CI step
  diffing the result; this runs the command as an action, so the declarations
  follow the config on every build and there is no drift to gate.

  ```python
  ts_worker_types(
      name = "worker_types",
      config = "wrangler.jsonc",
      node_modules = ":node_modules",
      wrangler_args = ["--strict-vars=false"],
  )

  ts_compile(
      name = "src",
      srcs = ["index.ts"],
      tsconfig = "//workers/api:tsconfig",
      types = ["../worker-configuration.d.ts"],
      types_srcs = ["//workers/api:worker_types"],
  )
  ```

  A macro over `ts_codegen`, with the generator shipped as
  `//tools/codegen:wrangler_types`. `wrangler_args` is the rest of the
  `wrangler types` command line verbatim -- `--strict-vars=false`,
  `--env-interface CloudflareBindings`, `--include-runtime=false`,
  `--env staging` -- so what a `cf-typegen` script runs today is what the
  target runs. Measured with wrangler 4.126.0 in the Bazel sandbox: the config
  and `node_modules` are the only inputs, the runtime half is generated by
  booting the `workerd` in `node_modules` over loopback with no network and no
  token, and two runs over one config are byte-identical. `srcs` is optional
  and its whole effect is `Cloudflare.GlobalProps.mainModule`, written when the
  file `main` names is staged.

  The output reaches a program the way a tsconfig names it -- a relative
  `compilerOptions.types` entry, with this target in `types_srcs` -- which is
  the pair Gazelle writes under a tsconfig that names the file. Gazelle now
  reads a `ts_worker_types` target in the tsconfig's own BUILD file and names
  it in `types_srcs` in place of the `tsconfig_types` filegroup, which it no
  longer writes for a file that is not in the source tree; the entry it
  rebases is unchanged. The package's nested editor program writes the entry
  through the `bazel-bin` symlink: on the fixture, 3 diagnostics (`TS2304` on
  `Env` and `ExportedHandler`) with the entry pointing at the source tree, 0
  with it pointing at `bazel-bin`.
